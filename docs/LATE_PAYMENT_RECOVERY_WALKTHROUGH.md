# Verified late-payment recovery

Implemented locally on 19 October 2026. Release frontend/backend together and restart the intended backend before use. Implementation does not reconcile production bookings automatically.

## Staff workflow

1. In **Public Customers**, select the booking's event and find its buyer/booking ID. Eligible **EXPIRED** rows showing **Payment received — needs review (booking_canceled_before_payment)** offer **Reconcile Payment** below that notice.
2. Compare the displayed booking, Paper.id invoice ID, full amount, buyer, venue/session and original seats against the **production Paper.id dashboard**. Verify full payment and that it has not been refunded. This action makes no provider API request; staff verification and a matching saved receipt are both required.
3. Select the verification checkbox, optionally enter a review note, and choose **Confirm Payment and Restore Booking**. The saved booking already supplies performer, session, ticket quantities and original seat selections; there is no repeated performer/session selection.
4. Success changes the booking to **PAID**, marks its original recoverable chairs/physical ownership **booked**, marks the receipt **processed**, and counts capacity once. Expand **Order Details** for the verifying staff email, invoice and note. An **Expired** filter hides the recovered row; select **Paid** or **All Payment Statuses**.
5. The server attempts the normal confirmation email only for the request that performed recovery. Failure leaves payment committed; refresh and use **Resend**. SMTP acceptance is not inbox proof. Duplicate recovery does not resend. If the HTTP acknowledgement or delivery is uncertain, refresh and check persisted status/delivery before retrying or using Resend.

Saving prevents repeated submission, modal dismissal and event switching. Errors retain the review/note. An unsaved review disappears with its row on event change. Refresh failure after success does not report the committed payment as failed.

## Scope and conflict handling

The first action supports **version-2, numbered competition** bookings (`winner`, `public_competition`) in Paper.id mode, with a matching saved paid receipt stopped specifically for expiry. Original partial selections are retained; tickets without selected chairs use existing **Assign Missing Seats** after payment. Direct orchestra, legacy complimentary/Masterclass quotas, historical-version bookings and other receipt reasons require separate staff review.

The owner selected **stop for staff review** if an original chair is taken or blocked. The transaction verifies the saved session/layout/tier, selected chairs, every physical alias, canonical ownership, and conflicting chair references in other active bookings. It can restore this booking's leftover locks or available original chairs and missing/inactive canonical ownership when all checks pass. It does not overwrite another owner/block or select replacements.

Capacity is compared with every other active booking in the exact event/venue/date/session, including pending holds and unresolved failed purchases, plus fully verified retained reservations on other expired bookings. The saved counter must equal either that other demand (target already released) or that demand plus the target (target stayed counted). Recovery writes the latter total once. Physical blocked-chair counts must match the saved block counter; restored demand plus blocks must fit each layout tier. Unexplained drift, missing counter, changed session/layout, more than 1,000 session booking records or excessive alias writes rejects the whole operation without changes.

The 19 October retained-hold correction proves another expired booking's entire purchased quantity against its distinct original selected chairs, active matching canonical ownership, exact paid-pool capacity reservation and original session/layout/tier. It preserves that other booking, ownership and chair aliases. Fully released or reassigned ownership is not counted again. Partial ownership, an unselected remainder, invalid references and unexplained no-seat expired demand still stop for review. Extra ownership reads are bounded to 400 distinct keys and original chair reads by that set; all reads precede writes in the existing transaction. The normal checkout capacity helper is unchanged.

All payment/seat/ownership/capacity/receipt changes share one authenticated transaction. Repeated/lost-response requests return already-paid without another inventory write or email. Email follows the commit; process interruption before dispatch and uncertain SMTP acknowledgement require staff delivery review. Later paid callbacks converge on the processed receipt.

## Endpoint and audit

`POST /api/v1/apcs/public-ticket/admin/reconcile-expired-payment` accepts `{bookingId, eventId, invoiceId, receiptId, amount, seatIds, confirmedPaid: true, note}` with the existing verified Firebase-token/exact-whitelist middleware. Submitted identity, total and original chairs must still match the stored booking. The receipt's booking/invoice identity, paid state, reported totals and currency must match. Verification is recorded as `admin_paper_dashboard`, not a fresh Paper.id API check.

Existing collections only: `publicBookings`, `ticketPaymentReceipts`, `seats{eventId}`, `ticketSeatOwnership`, `ticketCapacity`. Booking `paymentReconciliation` and receipt `reconciliation` store invoice/receipt IDs, amount/currency, actor, note, server time, prior status/reason and capacity before/after. Historical expiry/cancellation metadata remains. Ticket prices/quantities, contacts, performance identity, original seat labels, orchestra entitlements, schedules, assignment snapshots and redemption claims are preserved. Recovery restores downstream paid entitlement; it creates no redemption or orchestra assignment. Existing assignment coverage rules still apply. No collection, rule, index definition or migration is added; deployed index availability for the existing exact-session equality-query pattern remains acceptance work.
